# KCircle MVP PRD

> 慶應義塾大学 公認サークル 専用 소개 웹앱

---

## 핵심 정보

**목적**: 慶應義塾大学 신입생이 수백 개의 공인 서클 정보를 온라인에서 빠르게 필터링하고 비교하여 가입할 서클을 결정할 수 있게 한다.
**사용자**: 慶應義塾大学 재학생 (특히 신입생)과 서클 대표자 — 公認サークル / 公認学生団体 / 体育会 소속만 대상으로 하며, 비공인·인카레는 제외.

---

## 사용자 여정

### Flow 1 — 서클 찾기 (검색 플로우)

```
1. 상위 페이지 (トップ)
   ↓ 검색바 입력 또는 카테고리 탭 클릭

2. 서클 목록 페이지 (サークル一覧)
   ↓ 카드 클릭

3. 서클 상세 페이지 (サークル詳細)
   ├── 하트 버튼 탭
   │   [미로그인] → 로그인 페이지로 리디렉션 → 로그인 완료 후 상세 페이지로 복귀
   │   [로그인 완료] → 즐겨찾기 페이지에 저장
   │
   └── 「参加する」 버튼 탭 (당근 모임 패턴)
       [미로그인] → /auth/login?next=/circles/{id} 리디렉션 후 복귀
       [로그인 완료] → 채널 선택 모달 표시
                       → 사용자가 채널 선택 (Instagram / X / LINE 중 등록된 것)
                       → Postgres RPC `increment_inquiry_count(circle_id)` 호출
                         (SECURITY DEFINER 함수로 RLS 우회 — 컬럼 단위 권한 분리)
                       → inquiry_count += 1 (세션 1일 1회 디바운스 클라 + 서버 이중 보호)
                       → 새 탭으로 외부 URL 오픈

4. 즐겨찾기 페이지 (お気に入り) → 비교 페이지 (比較)로 최대 3개 송출
```

### Flow 2 — 서클 등록 (등록 플로우)

```
1. 회원가입 페이지 → @keio.jp 이메일 인증 → keio_verified=true 설정

2. 서클 등록 폼 페이지 (サークル登録)
   ↓ 서클 정보(이름, 카테고리, official_type 등) 입력 후 제출

   → status='pending' 으로 DB 저장
   → 「審査中」 안내 페이지로 이동

3. 관리자 승인 대기
   ↓ 관리자가 승인 큐 페이지 (管理者承認) 에서 공인 여부 직접 검증

   [승인] → status='approved' → 서클 목록 페이지에 공개 + 오너에게 이메일 알림
   [거절] → status='rejected' → 오너에게 거절 사유 안내 (예: 「公認サークルとして確認できませんでした」)
```

### Flow 3 — 즐겨찾기 및 비교 (お気に入りフロー)

```
1. 서클 상세 페이지에서 하트 탭
   ↓
   [미로그인] → 로그인 페이지로 리디렉션
   [로그인] → favorites 테이블에 insert

2. 즐겨찾기 페이지 (お気に入り)
   ↓ 비교 버튼으로 최대 3개 선택

3. 비교 페이지 (比較) → 활동빈도/연회비/태그/합숙유무 횡열 비교
```

### Postgres 함수 (RPC) — F012 `inquiry_count` 갱신용

**문제**: F012의 「参加する」 클릭은 **일반 로그인 사용자**가 `circles.inquiry_count` 를 +1 해야 합니다. 그러나 circles 테이블의 update RLS는 owner·admin 으로 제한되어 있어 그대로 두면 `403 forbidden` 이 발생합니다. Supabase RLS는 행 단위가 기본이며 컬럼 단위 update 권한 분리는 별도 정책 또는 함수 분리로만 구현됩니다.

**채택안**: Postgres 함수 `increment_inquiry_count(p_circle_id uuid)` 를 **`SECURITY DEFINER`** 로 정의하여 호출 시 함수 소유자(예: `postgres` 또는 전용 role) 권한으로 실행하도록 분리합니다. 이로써 RLS 모순을 피하면서 영향 범위를 「1 컬럼·1 증가 연산·`status='approved'` 행만」으로 제한합니다.

```sql
create or replace function public.increment_inquiry_count(p_circle_id uuid)
returns void
language plpgsql
security definer
set search_path = public
as $$
begin
  -- 인증되지 않은 호출 차단 (anon key 직접 호출 거부)
  if auth.uid() is null then
    raise exception 'unauthorized' using errcode = '42501';
  end if;

  -- 公開 중인 서클(approved)에만 카운트 허용
  update circles
     set inquiry_count = inquiry_count + 1
   where id = p_circle_id
     and status = 'approved';
end;
$$;

-- 권한 정리: 익명 호출 금지, 인증 사용자만 EXECUTE 가능
revoke all on function public.increment_inquiry_count(uuid) from public;
grant execute on function public.increment_inquiry_count(uuid) to authenticated;
```

**클라이언트 호출 방식 (Next.js Server Action 안에서)**:

```ts
// app/circles/[id]/actions.ts
"use server";
import { createClient } from "@/lib/supabase/server";
import { revalidatePath } from "next/cache";

export async function incrementInquiryCount(circleId: string) {
  const supabase = await createClient(); // server.ts — 매 호출 새 인스턴스
  const { error } = await supabase.rpc("increment_inquiry_count", {
    p_circle_id: circleId,
  });
  if (error) throw error;
  revalidatePath(`/circles/${circleId}`); // cacheComponents 환경의 stale 회피 (H-NEW-1 대응)
}
```

**왜 service role 키 + Server Action 직접 update를 채택하지 않았는가**:

- service role 키는 모든 RLS를 우회할 수 있어 1회 유출 시 전체 DB가 위험
- RPC + SECURITY DEFINER 는 함수 내부에서만 권한 상승 → 영향 범위가 함수 본문(1 컬럼·1 연산)으로 한정
- 디바운스/상태 검증을 함수 내부에 둘 수 있어 보안 정책을 한곳에 집중 가능

**서버측 디바운스 확장 (라운드 2 M-NEW-2 대응 예정)**: 추후 `inquiry_events(user_id, circle_id, day)` UNIQUE 제약 테이블을 추가하여 함수 내부에서 일별 중복 호출을 차단하면 KPI 정확도를 추가로 보강할 수 있습니다.

## 公認 검증 워크플로우

> MVP 단계에서는 시드 리스트 자동 매칭을 사용하지 않고, **「@keio.jp 메일 인증 + 관리자 수동 검증」** 의 이중 게이트로 公認 사칭을 방지합니다.

```
[대표자] 회원가입 (@keio.jp → keio_verified=true)
    ↓
[서클 등록 폼] 서클명·카테고리·official_type 등 입력
    ↓ 「公認サークルであることを誓約します」 동의 체크 후 제출
    ↓
[시스템] status='pending' 으로 DB 저장
    ↓ 오너에게 「審査中」 안내, 관리자에게 신규 신청 알림
    ↓
[관리자] /admin/circles 에서 pending 목록 확인
    ↓ 慶應義塾大学 公式 公認団体名簿(PDF) 등 외부 자료와 직접 대조하여 검증
    ↓
    ├── [승인] → status='approved' + 오너 이메일 알림 「サークルが公開されました」
    └── [거절] → status='rejected' + 거절 사유 입력 + 오너 이메일 알림
                  (예: 「公認サークルとして確認できませんでした」)
```

**MVP 운영 가정**: 서클 등록 신청량은 출시 직후 적으므로 관리자 1인의 수동 검증으로 대응 가능. 향후 신청량이 늘어나면 시드 리스트 자동 매칭(F005 확장)을 Phase 2 이후 도입 검토.
